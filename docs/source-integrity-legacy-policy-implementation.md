## 何を保持できるか

`integrity_legacy.py` は、10月26日固定triageの具体的な2,429 review_idと元レコード・根拠をhash固定したscopepackを使う。分類は出典未確認1,223、告知別名欄603、本文言及567、非名称欄33、Weak/Strong矛盾3。ワイルドカードや将来の追加は許可しない。

対象の元行が完全一致する場合だけ、候補masterの既存リスクタイプ・確認フラグ・備考へ未確認表示を追記する。元リスクタイプも残し、名称、キー、有効状態、リスク度、出典・カテゴリ、名称variants、登録/更新日時は変えない。元行と元根拠はscopepackと既存証跡に残る。元資料や本人同一性、現在掲載、当初の取込意図を復元できたとは扱わない。

`prepare` は専用の新規ディレクトリに候補CSVと **DRAFT** JSONを作る。業務用data/dist内への出力と既存出力の上書きを拒否する。正式な追加/掲載終了のイベントは作らない。

```bash
python -m src.integrity_legacy --prepare \
  --reviewed-at 2026-10-26T00:00:00Z --expires-at 2026-11-25T00:00:00Z \
  --out-dir /tmp/legacy-candidate-new
```

上記日付は再現用の提案日時。本番では実承認時に改めて範囲・日時・期限を確認する。このコマンドの出力だけで承認済みにはならない。

## 公開ゲートの条件

専用の `data/review/integrity_legacy_acceptances.json` を設ける設計だが、今回そのファイルを本番データに作成していない。実運用で使う際は別途承認を得て、承認者・理由・厳密UTC日時・期限と、各元/付記後review_id、付記後master行hash、分類、元根拠hashを記入する。

DRAFT、不正構造、未承認対象、重複、未来の承認日時、30日を超える期間、期限切れは公開停止。承認後の行や公式/過去原本の意味上の関係が変化した場合も自動追随せず、再判断を要求する。単に原本全体の別箇所が変わった場合は、同じ意味上の関係に対するIDを維持し、新しい原本hashを別途記録する。

OFAC/財務省の名称・Alias欠落、掲載状態、Party ID・出典関係、取得/解析/hash/証跡の失敗、未承認の誤生成・重複は免除しない。既存の通常保持承認とは分け、`legacy_accepted` と未確認分類・期限を記録する。承認後もfindingは残り、結果はREVIEWでありPASSにはならない。
