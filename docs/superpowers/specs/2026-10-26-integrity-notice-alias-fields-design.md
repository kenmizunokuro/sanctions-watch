# Phase 1 公式発表の明示別名欄の監査

出典未確認1486件のうち、本文の連続文字列では見つからない姓名順表記を、保存済み公式発表の明示a.k.a./f.k.a.欄へ結ぶ。探索で263名称に候補があった。本文言及だけの追加では語順違いを拾えず、語順の総当たりは同名誤認を増やすため、明示マーカーのフィールドだけを独立に読む実装を選ぶ。これは実装者の選択で、保持や同一性の承認ではない。

## Contract

- 既存の本文HTML読取を公開 `read_records(body)` として再利用し、別名マーカーと対応する括弧・引用符・区切りを独立解釈する。取込用パーサは使わない。
- 原文のa.k.a./f.k.a.、全文レコード、節/小見出し、フィールドとグループの文字位置、URL/hashを記録する。名称キーは既存match_keyによる正規化照合で、fuzzy/単語並べ替えはしない。
- 関連先欄だけの名前は明示別名として扱わない。括弧内にある別の関係の別名、閉じていない括弧/引用符、未知マーカーや区切り不正は部分採用せず解析失敗。解析できないことを変更なしにしない。
- 新しい分類NOTICE_ALIAS_FIELD_REVIEWは原本中の別名欄に対応候補があるという意味のみ。current=false、Party ID/Weak品質不明、保持対象外。過去掲載/元master同一性/現在状態/解除の証明へ昇格しない。
- 過去名簿や現行原本による既存の強い根拠を上書きしない。新しい根拠で旧承認IDを移植しない。故障時はtriage失敗と公開停止の証跡を残す。
- master/state/raw/Alias履歴・Apps Script不変、保持承認0、削除/解除/Phase2/mergeなし。旧証跡は別名保存。

## Output

独立リーダー、triage統合、実bash回帰、全件結果と原文フィールド対応、PENDING候補、追加判断一覧、前回からの差分、再現手順。基本監査の必須名集合や承認適用は変更しない。
